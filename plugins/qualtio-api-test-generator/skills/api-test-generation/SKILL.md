# API Test Generation

Generates REST API tests of two types and only two.

| Type | What it validates | Source of truth |
| --- | --- | --- |
| `integration` | That the service responds as expected end to end over HTTP | Repository conventions, and OpenAPI if it exists |
| `contract` | That responses comply with the declared schema, status codes and fields | **Mandatory**: OpenAPI specification |

## Always Load

Always load these references before generating anything:

- [references/stack-detection.md](references/stack-detection.md): how to detect the stack and what to reuse
- [references/reporting.md](references/reporting.md): mandatory structure of the final report

Load on demand:

- [references/openapi-contract.md](references/openapi-contract.md): only on the `contract` path

## Routing

1. If the user says `contract`, `schema` or `OpenAPI`, it is the `contract` path.
2. If the user says `integration`, `end to end` or describes a flow with several calls, it is the `integration` path.
3. If the user does not say, choose `integration`. It is the default.
4. If the request spans both types, resolve them one at a time and keep files, validation and report separate per type.

## Entry gate for the contract path

A contract test without a contract is not a contract test. If the user asks for `contract` and there is no OpenAPI specification locatable in the repository or provided by the user:

- stop,
- ask for the specification,
- do not replace it with the controller code or with observed responses.

## Procedure

1. Detect the stack following `stack-detection.md`.
2. Locate the source of truth: OpenAPI specification, or repository conventions if there is no specification.
3. Locate the existing test structure and the narrowest validation command that covers it.
4. Generate the smallest runnable change set possible.
5. Mark every generated test according to the `AI_SUPPORTED` convention of the detected stack.
6. Run the scoped validation command. If it fails, fix and run **the same** command again before widening the scope.
7. Return the report with the exact structure from `reporting.md`.

## Dependency rules

- If the repository has a starter, a BOM or an aggregator module that already covers the HTTP client and the assertions, use it. Do not declare granular dependencies beneath it.
- If support is missing, add the aggregator first and validate again. Only if no aggregator exists, add the minimal concrete dependency.
- Do not duplicate configuration inherited from the parent project.

## What not to do

- Do not invent endpoints, payloads, response codes or coverage claims.
- Do not modify pre-existing tests that are not marked as generated by this plugin.
- Do not run the full repository suite to validate two tests.
- Do not convert existing unit tests into API tests: create new files.
